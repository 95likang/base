生成式 UI 技术规格（v0.1）
0. 范围
本期做：在已有后台页面里，用一句话提问，现场生成一张数据卡片或图表，插进对话流。

本期不做：整页界面由模型生成、模型直接生成可执行代码在浏览器跑、写操作（下架、删除、退款）由模型直接执行。凡是改状态的按钮，一律走人在前端点击、后端以当前登录态重新鉴权和校验。

总判据（贯穿全篇两条）

结构的形状能在开发期穷举 → 用模板填数，不交模型。
屏幕上给出的确定性，不得超过手上真实信息的确定性 → 缺值不补、失败不静默冒充成功。
1. 概念与判据（对应第一部分）
1.1 什么交给模型
请求	处理方式	依据
「近 30 天营收」	模板填数	字段、图形、区间都固定
「上周 vs 上上周退货率并排比」	模板填数	形状明确，只是参数不同
「10 月哪几个渠道掉得最厉害」	现场生成	看哪条线、对比谁、怎么排，开发期穷举不完
「导出一份给会计的明细」	先做后端接口，模型只负责触发	要产出真实文件字节，前端重算不出来
1.2 不要用可变性做判据
「数据每天在变」不构成现场生成的理由——每日营收也在变，照样模板填数。唯一判据是形状能不能在开发期穷举。

2. 路线（对应第二部分）
路线	模型交出什么	在哪执行	本期采用
A 配置字段	填参数	浏览器	✅ 主路线
B DOM 树	节点树	浏览器	❌
C 服务端组件	组件代码/序列化产物	服务端	❌（本期无内网数据源需求）
决定：走 A。模型只输出 JSON 参数，组件是前端写死的 React 组件。

理由：组件实现由我们控制，模型能影响的只有参数，攻击面和降级范围都可控。

验收：全局搜索确认没有任何一条路径把模型输出当代码执行——不用 eval、不用动态 new Function、不渲染模型给的 HTML 字符串。

3. 组件注册表（对应第三部分）
3.1 目录结构
text

复制
src/
  genui/
    tools.ts          # 服务端：工具定义（description + schema）
    registry.ts       # 前端：name -> 组件
    validate.ts       # 前端：校验与语义规则
    render.tsx        # 前端：一个 part 走完校验到渲染
    components/       # 实际组件
    server-action.ts  # 点击回传
3.2 组件清单（首期 6 个）
name	用途	必需参数	可选参数
MetricCard	单指标 + 环比	label, value	delta, unit
BarChart	分类对比	series[]	title
LineChart	趋势	points[]	title
Table	明细列表	columns[], rows[]	pageSize
ComparePanel	两项并排	left, right	title
Callout	一句结论 + 高亮	text	level
3.3 命名与版本
name 用 PascalCase，与 React 组件同名，不带版本号。
组件结构变更不兼容时，新增 name（如 MetricCard2），旧的在注册表里保留至少一个发布周期。
禁止模糊匹配：收到未注册的 name 一律走降级，不做「猜最像的那个」。
3.4 注册表的强制约束
typescript

复制
// registry.ts
import type { ComponentType } from "react";
export const registry: Record<string, ComponentType<any>> = {
  MetricCard, BarChart, LineChart, Table, ComparePanel, Callout,
};
必须是显式白名单，不允许 import * as 自动收集。自动收集会让新增组件在没人复核的情况下对模型开放。
新增组件必须同时提交：组件实现、schema、description、一条 golden 测试用例。
4. 工具定义与调用（对应第四部分）
4.1 服务端
typescript

复制
// tools.ts
import { tool } from "ai";
import { z } from "zod";

const series = z.array(z.object({
  label: z.string().min(1).max(40),
  value: z.number().finite(),
})).min(1).max(50);          // maxItems 是强约束，写进 description 的只是建议

export const renderBarChart = tool({
  description:
    "渲染一张分类对比柱状图。仅在用户要求对比多个分类的数值时使用。" +
    "单一时序趋势请用 renderLineChart，不要用本工具。",
  inputSchema: z.object({
    title: z.string().max(60).optional(),
    series,
  }),
  // 纯渲染型工具，不写 execute：服务端无事可做，前端负责画
});
版本提示：inputSchema 是我所用版本的字段名；早期版本叫 parameters。装好后先跑一个最小例子确认字段名和消息结构（parts 形态），再往下写。

4.2 硬规则
description 是模型唯一的判断依据。模型看不到组件代码、看不到类型定义。两个工具用途相近时，description 必须显式写出「什么情况用哪一个」，不能只写自己的用途。
强约束只在 schema 里。提示词写「最多 200 行」拦不住，max(50) 才能拦。
参数里的数字不能来自模型想象。凡是模型生成的图表数值，必须来自同一回合的工具查询结果，由它回填。若查询与渲染是两个工具，必须保证串行（第二次调用的参数来自第一次结果），不允许并发发出。
纯渲染型工具一律不写 execute，避免服务端白跑一趟并产生额外一轮模型调用。
4.3 卡片身份与「再画一张 / 换掉那张」
每张卡片在写入历史时打上稳定 cardId（服务端生成，如 c1、c2），随消息一起入库。
「换成折线」这类改写，必须显式指定 targetCardId；模型没给就别猜，直接问用户指的是哪一张。
模型自编的编号不可信，前端按 targetCardId 精确比对，不做范围推断。
5. 流式渲染（对应第五部分）
5.1 决策规则
先判断一件事：后到的内容会不会改写前面已经上屏的内容。

场景	开不开	理由
单张卡片，字段陆续闭合	开，逐字段填充	每个字段只写一次，不回改
多张独立卡片依次到达	开	追加型，不推翻阅读位置
结论卡片，最终判断可能反转前几项	不开	中途状态会被后续推翻，看到的是错的
数据源本身 300ms 返回	不开	省下的等待看不见，白付复杂度
5.2 落地方式
前端按 part 增量接收，字段未闭合时用等宽占位撑住宽度，闭合即切真值，避免布局跳动。
骨架屏只用于「外框已建、零字段闭合」这一个阶段，不能用来遮住半截数字。
骨架屏不做校验，只买观感一致。
验收：卡片数值从 128 变 1280 的跳变要处理——数字位数变化不引起行高或列宽变化。

6. 安全边界（对应第六部分）
6.1 信任模型
模型输出等于外部输入，与用户表单提交同级。任何 part 在渲染前必须校验；任何字段在传给组件前必须重新构造，不允许 {...part.input} 直接透传。

6.2 硬规则
组件里禁止 dangerouslySetInnerHTML。富文本字段统一走纯文本渲染。
链接只允许白名单域，href 一律转义，target 固定 _blank 加 rel="noopener noreferrer"。
若未来引入 HTML/JS 任何形式的执行（本期不做），必须换源隔离到独立域，并配 CSP 兜底——allow-same-origin 与 allow-scripts 同时给，沙箱等于失效。
写操作接口的核验清单（以「批准付款」为例）：申请人身份、单据当前状态、当前登录人是否为该环节签署人、是否本人自批（禁止）、金额与币种一致性。抽象写「角色权限」不算数，要能落到具体字段。
前端按钮只是提示，真正的判断在后端用当前登录态重查。
验收：把一张卡片的所有字段替换为 "><script>、javascript: 链接、超长字符串，页面不崩、不执行、不出站。

7. 交互回传（对应第七部分）
7.1 硬规则
卡片上的任何点击，必须先成为一条用户消息事件，再进入下一轮。不允许只改前端局部状态就当作交互完成。

typescript

复制
// server-action.ts（示意）
"use server";
export async function onCardAction(cardId: string, action: string) {
  // 1. 后端以当前登录态重新鉴权 + 校验单据状态
  // 2. 把这次点击写成一条用户消息（结构化事件，非自然语言猜谜）
  // 3. 由消息历史驱动下一轮
}
7.2 状态写入历史，不回查
点击后的结果作为新事件写进消息历史，历史里存的是当时的快照：查到了什么、什么时候查的。
禁止在重放历史时回查数据库重算——那等于让模型把过去的事实读成当前事实。
会话恢复靠历史重放：前端从历史里取出所有 tool part，重新过一遍注册表还原卡片。这一步必须可用，否则「把第一张图换成折线」这类追问全部失效。
验收：刷新页面后卡片全部还原且数值与生成时一致；三天后打开同一会话，卡片显示旧数并标注生成时间，不会静默变成新数。

8. 降级与容错（对应第八部分）
8.1 三层，各管各的
层级	触发条件	表现
块级	单个 part 校验失败 / name 未注册	原位占位卡 + 原始 payload 与 messageId 记日志，其余块照常渲染
消息级	整条消息无任何可用块	退纯文本，保留模型说过的话
会话级	渲染器抛未捕获异常	只有这一种情况才允许整块兜底
绝对不允许：一个块坏了就丢掉整条消息。

8.2 校验与补值
typescript

复制
// validate.ts
const parsed = schema.safeParse(part.input);
if (!parsed.success) return { ok: false, reason: "shape" };
// 形状过了还要过语义
if (parsed.data.value === 0 && parsed.data.delta === undefined)
  return { ok: false, reason: "semantic" };
补值规则，一句话：补完之后屏幕给出的确定性，不能超过手上真实信息的确定性。

字段	补不补	理由
color 缺失	补默认色	纯样式，不改变事实
series 缺失	不补	补空数组等于断言「没有数据」
MetricCard.value 缺失	不补，报「数据不完整」	补 0 会让人读出「值为零」这个错误结论
所有分项为 0 的饼图	改成「暂无数据」	校验通过但语义错，画出来是空圆环，会被当真实结果
8.3 是否告知用户
判据：这次失败的呈现会不会被误读成正确结果。 会 → 必须显式标注；不会 → 静默占位可接受，但日志必须留。

name 认识但缺必需数组 → 画出来长得完全正常，用户会当真实结果读走 → 必须显式。
name 完全不认识 → 屏幕上什么都不显示，用户知道这里没东西 → 占位即可。
9. 成本与缓存（对应第九部分）
9.1 两笔账
生成时按输出计费。
之后每一轮，卡片 JSON 作为历史按输入计费重发。会话越长，旧卡片被重发越多。
9.2 优化项（按收益排序）
做法	效果	代价
全部工具 schema 放 system prompt 前段	命中稳定前缀，逐轮复用	首轮贵一次，之后极便宜
卡片 JSON 留在历史里	保住可指代性	每轮重发
删掉旧卡片 JSON	省输入 token	模型失去「第一张图」这个指代对象，多轮追问直接失效
不要为了省 token 删历史卡片——前端还能渲染，用户看不出问题，但模型的追问能力已经断了。

9.3 延迟
schema 校验是本地毫秒级，不是瓶颈。
真瓶颈是：必须等整份 JSON 合规吐完，第一块内容才能上屏。
手段：减少字段嵌套层级、减少可选字段、把「先给一句纯文本结论」和卡片并行发出。
缓存大头在冷启动/过期重算，不在逐轮。
验收：一次完整提问到首屏可见 ≤ 3s（P50），失败率与重试次数进监控。

10. 产品判断与验收指标（对应第十部分）
10.1 上线前必须回答
这个入口解决的是「发现异常」还是「已知异常后的深挖」？
若是发现型场景，固定大盘是否该保留为入口，生成式只挂在每一行的「细问」上？
10.2 指标（三组一起看）
组	指标	用途
用量	提问次数 / DAU	只看它没有意义
正确性	生成结果被人工修改、丢弃、重问的比例	判断模型准不准
增量	大盘查看量是否下降、同事是否真去看了那张图	判断是否创造新能力
若涉及动作型输出（封禁、打标），必须配反向指标：解封数、申诉数、人工驳回数。单向指标会被模型误判推高，看起来像成效。

10.3 关停条件
上线一个月，提问量停在一试的量级、大盘查看量没降、且生成结果被丢弃比例超过三成 —— 三项同时成立，就该关，不必继续优化提示词。
